# Phase 0b: Windows engine spike report

- **Date:** 2026-11-20 / 21
- **Machine:** owner's desktop, Windows 11 Home 22H2 (build 22621.4317), 32 logical CPUs, 32 GB RAM, Intel UHD 770 + NVIDIA RTX 4090, two 1920×1080 monitors (both at 100% during automated runs).
- **WebView2 runtime:** Evergreen 157.0.4341.60 (from `BrowserVersionString` and the EdgeUpdate registry key).
- **Windows diagnostic data setting:** Required only (`AllowTelemetry = 1` under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\DataCollection`).
- **Spike:** `spikes/engine-spike/` (tao 0.37.3, wry 0.57.3, webview2-com 0.39.1, windows 0.62, adblock 0.13.6). Standalone, not in the workspace. How to run it: `docs/testing/phase-0b.md`.
- **Logs:** every result below comes from a log line in `%LOCALAPPDATA%\lwb-spike\logs\spike-<tag>.log`, produced by the scripts in `spikes/engine-spike/scripts/`. Re-running a script reproduces it.

## Summary

**Verdict: GO for Windows.** Every checklist item works, most of them fully; the caveats are recorded in DEC-015 to DEC-019 and none blocks Phase 1. The owner's hands-on checks (Google sign-in in normal and private views, Netflix, Disney+, Spotify, 150% scaling, overlay flicker) are in.

Most important findings:
1. **Everything the architecture depends on exists and works through wry + `webview2-com`:** several child views on one shared environment (one browser process), `TrySuspend`/`Resume`, audio state and mute, per-process frame mapping, request interception including service and shared workers, opener-preserving popups (normal and private), native accelerators, our own context menu, and every engine event on the checklist.
2. **Host scripts run in the page's main world, as the spec feared.** The page saw our global and intercepted our `chrome.webview.postMessage`. **The bundled-extension alternative works:** its content scripts run in an isolated world and can reach the host through a request to a reserved host name, which we answer ourselves, carrying a per-run token. Caveat: the extension does **not** run in private (InPrivate) views. → DEC-015.
3. **Memory: the empty window is 89 MB with the chrome view and 68 MB without** (private working set, median of 3), well under the 200 MB target. The chrome view costs ~21 MB, and the shell process is 7 MB (14 MB with the ad-block engine loaded). But **`MemoryUsageTargetLevel = Low` mostly *trims* memory to the pagefile rather than freeing it**: a hidden Wikipedia renderer went from 108 MB to 7 MB private working set, while its private commit only fell from 122 MB to 112 MB. Our §7.6 metric (private working set, what Task Manager shows) rewards trimming. → DEC-016.
4. **The chrome-view overlay works:** a transparent grown chrome view draws a dropdown over a live page, with the page visible around it, and shrinks back. Clicks on transparent pixels go to the chrome view, not the page (no click-through), which suits popovers that close on an outside click. The owner saw no flicker over ~45 open/close cycles with a video playing behind it.
5. **Privacy: wry silently disables SmartScreen** (its default browser arguments include `--disable-features=msSmartScreenProtection`), and **wry has no option for `IsCustomCrashReportingEnabled`**. So we create the single environment ourselves and pass it to wry with `with_environment`, which §6.4 wants anyway. `IsCustomCrashReportingEnabled = true` demonstrably stops Crashpad's upload attempts. Dumps stay in the profile's `Crashpad\reports`. → DEC-017 (telemetry details below).

**DRM streaming works, at HD on Netflix but only 480p on Disney+.** Netflix plays at 1080p over software Widevine, and Spotify plays. Disney+ stays at 854×480, which matches the engine reporting HDCP 1.4+ as `output-restricted` on this machine. Hardware DRM (Widevine L1 / PlayReady SL3000) isn't available, so no 4K/HDR. Whether Edge on the same machine gets the same HDCP answer is still open (one-minute owner check); it decides whether this is our embedding or the machine.

**Open items (none blocks the verdict):**
- Edge vs spike HDCP comparison (row 29).
- A5, the elevated pktmon + DNS-log capture, wasn't run. The follow-up inspection in Windows Sandbox or a VM (DEC-019) covers the same ground better.

## Telemetry (items 26 and 28)

_From the non-admin observation runs. The elevated capture (A5: DNS names, UDP/QUIC, the policy control) wasn't run; the Sandbox/VM follow-up in DEC-019 covers it._

**What Microsoft documents** ([WebView2 data and privacy](https://learn.microsoft.com/microsoft-edge/webview2/concepts/data-privacy), [ICoreWebView2EnvironmentOptions3](https://learn.microsoft.com/microsoft-edge/webview2/reference/win32/icorewebview2environmentoptions3), [ICoreWebView2Settings8](https://learn.microsoft.com/microsoft-edge/webview2/reference/win32/icorewebview2settings8), [WebView2 policies](https://learn.microsoft.com/deployedge/microsoft-edge-webview-policies), [enterprise](https://learn.microsoft.com/microsoft-edge/webview2/concepts/enterprise)):
- Data goes through Chromium/Edge telemetry, Windows data reporting, and Watson for crash dumps. **Required data is collected regardless of the Windows diagnostic setting**; optional data (API/SDK usage, creation failures, browser events) follows *Settings → Privacy & security → Diagnostics & feedback*. The page says the app has no control over overall collection.
- App controls are only (1) `IsCustomCrashReportingEnabled` (default false = follow OS consent; true = "Windows won't send crash data to Microsoft endpoint") and (2) SmartScreen via `IsReputationCheckingRequired` (default true, applies per user-data folder, and is also off whenever the Windows "SmartScreen for Microsoft Edge" setting is off).
- **Edge browser policies don't apply to WebView2.** WebView2's own policies (`HKLM\SOFTWARE\Policies\Microsoft\Edge\WebView2`) include `ExperimentationAndConfigurationServiceControl` (0 = RestrictedMode, which stops that service's communication; Microsoft doesn't recommend it), but none for diagnostic data or SmartScreen. Edge Update policies (`HKLM\SOFTWARE\Policies\Microsoft\EdgeUpdate`, e.g. `UpdatesSuppressed`, `AutoUpdateCheckPeriodMinutes = 0`) also govern runtime updates. These are machine policies, set by admins, not something an app ships.
- No hostnames are documented.

**Observed (non-admin):** `spikes/engine-spike/tools/observe-net.ps1` runs the spike per variant (one `about:blank` view, no chrome view, fresh profile). It idles 45 s, navigates to example.com, then 20 s later to Wikipedia. Every 250 ms it records the remote TCP endpoints of the `msedgewebview2.exe` processes whose command line contains that run's profile folder. Host names come from forward lookups (Chromium's own resolver bypasses the Windows DNS cache, so the cache named almost nothing).

Reading it:
- **SmartScreen** is the only host the app controls remove, and either control works. D16 can be decided on this basis: on = the visited URL's information goes to Microsoft on each navigation.
- **config.edge.skype.com and edge.microsoft.com remain with every app-level control on.** Short connections can slip between 250 ms polls (config.edge.skype.com appeared in B and E but not in A, C or D), so absence in one run isn't proof. Limits: TCP only (no QUIC remote addresses), polling, and required diagnostic data may be relayed by Windows' own diagnostics service, which isn't attributable to us. ## How each measurement was taken
- **Memory:** for each process, `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetProcessMemoryInfo` with `PROCESS_MEMORY_COUNTERS_EX2`. We report `PrivateWorkingSetSize` (Task Manager's "Memory (active private working set)") and `PrivateUsage` (private commit). The process set is our own pid plus `ICoreWebView2Environment8::GetProcessInfos` (never by process name). Totals are sums. Release build, sampled after a settle delay.
- **Handler latency:** `Instant` at handler entry → after `SetResponse`/return, pushed per request; engine-only time measured separately around `check_network_request`. Percentiles are nearest-rank. Release build.
- **CPU time:** `GetProcessTimes` (kernel + user) deltas over 10 s per process.
- **Synthesized input:** permissions, context menu and popups used DevTools-protocol mouse events (which count as user activation). Fullscreen and accelerators used real OS input (`SendInput`), because fullscreen rejects synthesized activation.
